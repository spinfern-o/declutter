WHAT IS DONE AND TESTED (backend)

- backend/train/classes.csv has a `prompts` column: a few plain phrases per class.
- backend/train/yoloe.py builds a YOLOE checkpoint from those prompts into
  train/runs/<checkpoint>/weights/best.pt. Every phrase is looked for on its own and a class scores as high
  as its best phrase. The saved file reports exactly the 20 class names and needs no text encoder.
- backend/server/test_app.py has a new test: the model in use must know exactly the classes in classes.csv.
- Measured in the cloud session:
    - the deployed model on the `model` release has 18 classes; it lacks `shelf` and `battery`, so the new
      test fails on it and passes with the YOLOE build (6 passed);
    - the built file loads through plain YOLO("best.pt") as YOLOE and predicts without the text encoder;
    - promote.py runs on it unmodified and its scoring reads the 20 classes;
    - averaging a class's phrase embeddings (the first plan) does not work for classes that hold different
      things: a bus fell from 0.96 to 0.10. That is why each phrase is scored on its own.
- Not known: how well YOLOE finds things in real cabinet photos. On one blurry desk photo it missed a
  pencil that the current trained model found, and plain YOLOE with the word "pencil" missed it too. No
  photo with shelves was available, so `shelf` detection is untested. On a 4-core cloud CPU the large
  checkpoint took about four times as long per photo as the current model.

PARKED: CORE ML (do not build now)

The owner first asked to move from Fly.io to Core ML, then chose to do the shelf work first. For later:
Ultralytics exports the YOLOE checkpoint to a single .mlpackage with the same 20 classes
(`format="coreml"`, runs on macOS or Linux, needs coremltools >= 9.0; pass `quantize=16` or it stays
32-bit and twice the size). Check that the head's fold (Unflatten, MaxPool3d, Flatten) converts. The app
then needs a Swift decoder for the raw outputs (boxes, NMS, masks from the 32 prototypes, plus the shelf
rules now in backend/detect.py `split`). The 3D item models can come straight from the public `models-3d`
GitHub release: its API lists each asset with a sha256 digest whose first 16 hex characters equal the
fingerprint the server sends today, so ModelStore.plan() works unchanged. After that backend/server/, the
Dockerfile, fly.toml and the deploy workflow can be deleted. Ultralytics and YOLOE are AGPL-3.0, which
matters for a closed-source App Store release.

Other Hugging Face models considered and why they lost: hugging-mac/yolov8-seg-coreml (COCO's 80 classes
only), mlboydaisuke/MobileSAM-CoreML plus apple/coreml-mobileclip (works without training but two models
and a bigger rewrite), apple/coreml-sam2.1-tiny (needs a tap per item),
apple/coreml-detr-semantic-segmentation (doesn't separate one item from the next),
mlboydaisuke/RF-DETR-CoreAI (.aimodel, iOS 27 only; the app targets iOS 26). These came from web search;
huggingface.co was blocked in the cloud session, so the model cards were not opened.
